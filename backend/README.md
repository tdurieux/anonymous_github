## Configuration

The backend reads environment variables, not `.env` files itself. Compose loads the environment file. Preserve the existing `SESSION_SECRET`, `CREDENTIAL_KEYS`, and `CREDENTIAL_ACTIVE_KEY_ID` to retain sessions and encrypted GitHub grants. It supports the existing MongoDB, Redis, OAuth, GitHub App and S3 variable names in `internal/server/config.go`.

For local execution, set `PUBLIC_DIR` to the root `public` directory and `FOLDER` to repository storage. Set `MONGODB_URI` explicitly when testing. `MONGODB_DATABASE` defaults to `production`; a database path in the URI takes precedence. Local HTTP testing requires `COOKIE_SECURE=false`; production behind HTTPS requires `true`.

`TRUST_PROXY` supports hop counts, IPs/CIDRs, and the existing named ranges. Configure it for the actual proxy topology; forwarded headers from untrusted peers are ignored. GitHub App private keys can come from `GITHUB_APP_PRIVATE_KEY_FILE` or the existing environment variable.

Anonymization defaults to one child process, a queue of 16, and a 512 MiB weighted admission budget. `ANONYMIZATION_WORKERS` permits up to four workers; `ANONYMIZATION_MEMORY_MB` controls admission. A child receives no server credentials. Its 384 MiB Go heap target is a soft limit; the container memory limit is the hard boundary. Input is capped at 100 MiB, output at 400 MiB, and execution at 15 seconds. Large concurrent downloads also consume temporary storage.

## Provider adapters

`internal/provider` defines repository access, metadata, commits, trees, file readers, public URLs and self-link prefixes. Optional `FileMetadata` supports per-file recovery from truncated trees. Optional `Discovery` and `Documents` interfaces cover repository lists/branches/readmes and normalized snippets/pull requests. `Discovery.List` receives `provider.ListRequest{OwnerID, Force}` so each adapter can implement its own cache and refresh policy. A fixture adapter verifies that the HTTP route forwards refresh requests independently of GitHub. The shared lifecycle, MongoDB publication, anonymization and file/ZIP handlers use these interfaces. GitHub protocol calls live in the GitHub adapter; stored ZIP repositories use the archive adapter.

Register another adapter with `server.New(config, store, adapter)`. Implement `provider.Repositories` and any optional capabilities you need. Its `Branch` method must resolve an actual branch, not a same-named tag, and return `provider.ErrBranchNotFound` only after establishing that the branch is absent. Authorization and temporary upstream failures must remain distinct. The registry rejects duplicate IDs and typed-nil adapters, and captures each adapter ID once. Lookups, ordering and advertised capabilities use that registered name even if an adapter later reports a different ID; extensions cannot replace built-in authentication by changing their ID during registration. Implementations live within the backend module because the interfaces are under `internal/`.

Create a repository with the existing `POST /api/repo` body and add `source.provider`, for example:

```json
{"repoId":"example","fullName":"team/subgroup/project","source":{"provider":"your-forge","branch":"main","commit":"opaque-revision"},"terms":["Alice"],"options":{"expirationMode":"never","link":true}}
```

Third-party bindings are stored in `providerAccess`; GitHub retains `githubAccess`. Existing GitHub source types without a provider field keep working. Unknown providers and unsupported capabilities fail explicitly. Updating a resource cannot switch its provider. Discovery and save operations validate the adapter’s declared provider and binding; metadata must contain a name and immutable ID and must agree with the connected repository ID. HTTP tests inject mismatched adapter responses and verify that they create neither cached repository metadata nor anonymous resources.

GitHub previews use positive numeric `gh_` IDs; other providers retain their own opaque IDs under their registered prefix. Invalid requests are rejected before provider calls. The returned repository identity must match the preview before branch or commit resolution and before cache writes. Missing branches return `branch_not_specified`; authorization, rate-limit and upstream failures retain their provider error category and reset time. Tests exercise the save handler's null case, preflight rejection, immutable-ID mismatches, wrapped branch failures and a successful opaque-ID reconnect.

## Performance results

Three alternating fresh Node and Go processes ran each fixture. The median measures transformation only, excluding startup, compilation, network, database and child-process overhead. Output SHA-256 hashes agree.

- 2 MB numeric input, 47 absent terms: Node 7.44 ms, Go 2.25 ms; Go 3.31 times faster.
- 100 MB numeric input, 47 absent terms: Node 234.29 ms, Go 117.23 ms; Go 2.00 times faster.
- 50 MB with sparse replacements: Node 509.48 ms, Go 593.56 ms; Go 1.17 times slower.
- 22 MB with 1.2 million replacements: Node 373.11 ms, Go 503.78 ms; Go 1.35 times slower.

These results do not support an overall speedup claim. The archive HTTP benchmark below measures one full-server workload. Shared-cache serving, external provider latency, cold start and GitHub rate-limit usage still need separate workload measurements. Raw repository content is cached through the shared provider layer on filesystem or S3 storage. ### Full-server archive HTTP benchmark

The following differences are deliberate or require staging review:

- Plaintext legacy GitHub tokens are not read. Complete the existing credential migration before cutover.
- An unbound legacy account is not linked automatically by matching its GitHub username. Existing authenticated owners need an administrator-verified identity recovery procedure. The old username-only linking behavior is unsafe.
- Repository claims require upstream admin permission or existing local ownership; public read permission alone is insufficient.
- Markdown project pages use the existing browser renderer in a sandbox without `allow-same-origin`. Rendering now requires JavaScript; a plaintext fallback is provided.
- Go file ETags use a separate namespace. Existing caches will revalidate. Archive contents are generated afresh; compressed ZIP bytes and timestamps are not expected to match Node.

The Linux overview supplies the existing browser fields for normalized one-minute CPU load, host memory, process RSS and root-filesystem usage. These preserve the TypeScript host-level meanings; they are not container quota utilization. Unsupported platform measurements are null. ### Cache telemetry

`CACHE_MONITORING_ENABLED` defaults to true. Go records provider-independent source cache hits, misses, fills, stored bytes, fill waits, admission bypasses and failures. Per-repository raw-cache reads use TypeScript's `legacy_source_hit` and `legacy_source_miss` labels and byte counts. Shared-cache reads use `source_hit` and `source_miss`, so the report does not mix the two cache paths. Request traffic is classified as file, website, ZIP, monitor or background; client-supplied telemetry labels are ignored. Events contain no paths, repository names, IDs, tokens or anonymization terms.

Recording uses a mutex-protected buffer capped at 512 minute/event/traffic groups. A worker flushes every five seconds with a three-second database deadline. MongoDB aggregates counts across instances; TTL indexes retain minute data for 48 hours and hourly data for 30 days. The admin report flushes local pending events, supports the same 15-minute, one-hour, one-day and seven-day windows, and sends `Cache-Control: no-store`. Concurrent flushes return an unavailable report instead of accumulating blocked requests. Failed batches are discarded without replay; the dropped count is a conservative upper bound if a write partially succeeded. Graceful shutdown flushes pending events.

The report returns the configured shared-cache state, filesystem support and live source/result budget summaries. Statistics remain visible when event monitoring is disabled, matching TypeScript. Missing optional caches produce null summaries; an unreadable cache index returns the generic unavailable response without partial statistics or internal error details. Shared decision and compression events enter the Go metrics buffer. The offline telemetry importer preserves TypeScript history in the Go report.

To transfer cache telemetry, stop the Node processes that write the shared cache and flush their pending metrics before shutdown. Use the original `telemetry.sqlite` with its adjacent WAL files, or a consistent SQLite backup. Copying only the database file while writers are running can omit committed history. Run from the repository root with its Node dependencies installed:

```sh
export MONGODB_URI='mongodb://127.0.0.1:27017'
export MONGODB_DATABASE='anonymous_github'
export CACHE_TELEMETRY_FILE='/absolute/shared-cache/telemetry.sqlite'
node backend/scripts/migrate-cache-telemetry.cjs dry-run
NODE_CACHE_WRITERS_STOPPED=1 node backend/scripts/migrate-cache-telemetry.cjs apply
```

The dry run validates the full read-only SQLite snapshot and prints row counts and its digest without writing to MongoDB. Apply requires the explicit stopped-writer acknowledgement. Import runs in batches of 500 with a two-million-row limit. A single manifest in `gocacheimports` binds the destination to this snapshot; a different snapshot is rejected. Interrupted runs can be resumed with the same source, and completed replays do not restore expired rows. This imports one deployment's shared telemetry database, not multiple independent histories. Retain the manifest until the migration is retired.

Imported counters use separate IDs in `gocachemetrics`, so concurrent Go events add to the report without replacing historical totals. Minute/hour buckets, latency buckets, dropped counts and original expiration times are preserved. Only known event and traffic labels are accepted, including TypeScript's `inspected_changed`, `inspected_unchanged`, `inspected_passthrough` and `inspected_binary` events and `legacy_source_hit` / `legacy_source_miss`; health hostnames and process IDs are hashed. The importer leaves SQLite unchanged. The integration rehearsal generates history using the actual TypeScript telemetry module, verifies all four Go report windows, resumes an interrupted import, checks concurrent retries and rejects changed or malformed snapshots.

### Transformed-file cache

Text-file requests now reuse successful worker outputs. Keys include a SHA-256 digest of the actual input, matcher version, normalized anonymization options, provider-specific self links, mask, hostname, repository identity and revision. Provider authorization and current repository revision are checked before reading source data and again before returning transformed output, including cache hits. Failed transformations are not cached.

Each Go process maintains a private temporary directory with a one-hour TTL, at most 128 entries, a 512 MiB retained-data budget and a 128 MiB per-entry admission limit. Identical concurrent requests share one worker result. Existing worker admission limits also bound input spooling and cache-copy concurrency. Cache failures fall back to transformation; malformed or truncated entries are discarded and repaired. Cache reset, removal, expiration and generation cleanup invalidate local entries. Maintenance prunes idle entries, and shutdown removes the directory. Replicas have separate caches; revision checks prevent reuse after a change handled by another replica.

The cache reports `legacy_result_hit` and `legacy_result_miss` through the admin telemetry endpoint. Integration tests cover byte-identical cached output, changed bytes under an unchanged provider revision, settings changes, reset, revoked access and eight concurrent reads launching one worker. This implements the legacy transformed-output fallback. Shared result-cache decisions are implemented separately below.

### Worker-cache measurements and cancellation

Run `go run ./cmd/cache-benchmark` from `backend/` to measure cold and warm worker paths. The command launches the actual isolated worker, runs seven samples per mode, hashes every output, and fails on an output mismatch or a worker launch during the warm phase. Cold samples remove that fixture's cached result before each run. Timings include input spooling/hashing, cache publication or copying, output reading/hashing, and cleanup.

The recorded development-host run in `reports/transformed-cache-benchmark.jsonl` measured these medians: 60 KB text, 15.13 ms cold / 3.28 ms warm (4.61×); 2 MiB with absent terms, 139.43 / 78.16 ms (1.78×); 2 MiB with replacements, 258.84 / 95.90 ms (2.70×); and 128 KiB JavaScript-boundary input, 58.41 / 6.17 ms (9.46×). Each warm fixture launched zero workers. These are seven sequential samples on a shared development host, not a TypeScript comparison or an HTTP throughput measurement. Provider access, authorization, MongoDB and Redis are excluded.

Input spooling, cache copying and cache publication check cancellation between reads. Canceled operations release admission slots and remove partial output. An arbitrary blocking `io.Reader` must still supply its own interruption mechanism; network readers retain their request context. Real-worker tests verify that tighter output limits cannot reuse larger cached output, failed transformations are not cached, and mask changes select a different result.

### GitHub README decoding

GitHub README previews apply the same `Buffer.from(content, encoding).toString("utf-8")` behavior as TypeScript. Contracts extracted from the actual TypeScript expression cover permissive standard/URL-safe base64, missing padding, ignored characters, invalid UTF-8 replacement, hexadecimal prefixes, UTF-16 unit narrowing and encoding aliases. This decoder belongs to the GitHub adapter; other providers continue returning normalized text through `Discovery.Readme`.

Invalid encodings and unsupported content shapes become `readme_not_available` (404) at the preview endpoint and do not overwrite a valid cached README. Decoded byte buffers, including array-like allocations and UTF-16 encoding expansion, are capped at 32 MiB (UTF-8 replacement text can be up to three times that size) to prevent a tiny upstream JSON object from requesting unbounded memory. This is an intentional bound beyond Node's permissive Buffer constructor. Integration tests verify decoded HTTP text, cached reads, branch JSON output and cache preservation on decode failure.

### HTTP response compression

Eligible API and static responses negotiate Brotli (quality 4), gzip or deflate using the TypeScript middleware's preference rules. Known-length responses below 1 KiB stay uncompressed; unknown-length streams can compress immediately. `Vary: Accept-Encoding` is retained even for eligible responses below the threshold. `Cache-Control: no-transform`, existing non-identity content encodings, HEAD requests and noncompressible MIME types prevent compression. Repository file routes remain excluded, and the GitHub webhook stays before the compression middleware, matching TypeScript's mount order.

The wrapper streams through bounded compressor buffers, preserves flushing and response-controller access, removes stale content lengths, and propagates cancellation and write failures. It does not buffer an entire streamed response. JSON responses provide their encoded length before header commitment so the threshold applies correctly. MIME compressibility data is generated from the installed `mime-db`, including explicit false entries.

`contracts/compression.cjs` runs 117 HTTP cases through Express with the actual compression options extracted from `src/server/index.ts`. Go tests compare negotiated encoding, Vary, content length, status and decoded body hashes. Compressed bytes may differ between compressor implementations; decoded output must match. Additional tests exercise static responses through `Server.ServeHTTP`, webhook exclusion, flushing, failed writers, cancellation and HTTP/2.

### JSON output and conditional responses

JSON responses now use compact output and strong ETags derived from the transmitted JSON bytes. The shared response path handles GET/HEAD/QUERY freshness, weak validators, validator lists, wildcards, `Cache-Control: no-cache`, and If-None-Match precedence over If-Modified-Since. It strips entity headers and bodies for 204/304 responses and suppresses HEAD bodies. File revalidation uses the same validator matching rules. Authentication, local permissions and provider authorization still run before returning 304; integration tests cover unauthenticated users, strangers and revoked provider access.

Sixty-six HTTP fixtures run through Express with the application's strong-ETag setting and compare status, body, content type, length and ETag. JSON U+2028/U+2029 handling matches JSON.stringify without changing literal backslash escapes. Go map keys retain deterministic sorting, so tags are computed from Go's actual response order rather than assuming TypeScript insertion order.

Non-finite numeric values serialize as null. Invalid provider values or cyclic/excessively nested data produce a structured 500 before committing a successful status; internal encoder errors are not exposed. Response normalization caps nesting at 100 levels to bound recursive processing, and custom JSON encoders still receive normal serialization error handling. Maintenance-token creation defers its 201 status until encoding succeeds. Failed network writes abort the response instead of appending an error document to partial JSON.

Response recovery tracks header commitment beneath compression, including routes that bypass compression. Panics before final headers return a generic 500 and discard stale file/download headers. Panics or route errors after headers abort the connection, matching Express finalhandler, without appending JSON or completing a truncated compressed stream. Real HTTP tests cover plain and gzip streams, explicit aborts, flush-only responses, and recovery after informational 103 headers. Panic values are never included in the error response or request-panic log.

### Provider quota delays in background jobs

Preparation jobs that receive a provider quota error enter `delayed` until the reset instant. The admin API reports them as delayed, and maintenance enqueue cannot reset their deadline. Quota delays do not consume the three ordinary failure attempts or increment completed/failed queue metrics. Repository status becomes `queue` with the existing `rate_limited:<milliseconds>` message, so the public response retains its retry time. Missing or expired reset times use a one-minute fallback. Resource revision checks protect concurrent removal/reconnect, and job lease checks protect replacement workers. Successful retries clear the quota message and stale job error fields.

Adapters can return `provider.RateLimitError{ResetAt: ...}` or `provider.ErrRateLimited`; they do not need GitHub-specific job logic. The GitHub adapter supplies reset times from `X-RateLimit-Reset` and `Retry-After`, taking the later valid instant. Its existing public error code stays unchanged. Integration tests exercise repeated quota delays on the last ordinary retry, delayed claim eligibility, stale leases, concurrent removal, successful publication and the actual worker loop with a non-GitHub adapter.

Go uses a separate queue. Existing BullMQ work can be imported with the offline handoff tool below; starting Go alone does not migrate it.

### Shared provider quota gates

`internal/quotagate` stores provider/scoped reset times in Redis and a bounded 2,048-entry local fallback. Scope keys are SHA-256 hashes of an unambiguous provider/scope pair. Redis contains only the hash and reset timestamp. Atomic updates retain the latest reset under concurrent writers; expiry releases scopes automatically. Redis failures preserve observed local limits and permit unknown scopes, matching TypeScript's best-effort quota coordination. Cancellation stops the caller before an upstream request.

GitHub API, blob and raw-file requests check the gate before dispatch. Quota responses extend it; a known limit returns the existing 429 error immediately, allowing background jobs to release their slot and enter the delayed queue. This differs from TypeScript's in-request sleep: Go does not hold an HTTP request open for a long provider cooldown. Existing resource authorization still runs and a quota gate never authorizes access. Blob quota errors no longer trigger another request through raw fallback.

App-user scopes survive access-token renewal, installation scopes span repository-scoped token renewal, and App scopes survive JWT renewal. OAuth tokens use their digest as the scope; anonymous calls share the anonymous scope. Credential-to-scope registrations store token digests and are bounded to 2,048 entries. Go uses its own hashed Redis namespace and imports active TypeScript `gh_rate_gate:` records when a credential is used. It checks both the token-hash key and the applicable installation/App-user key, preserving the latest valid reset. Imported records survive in Go after the legacy keys expire or are removed; later TypeScript extensions are picked up on subsequent checks. Legacy records are never changed or deleted by Go, and a shorter legacy delay cannot shorten a Go gate.

Other adapters can construct `quotagate.New(store.Redis)`, call `Current(ctx, providerID, scope)` before upstream requests, and call `Extend(ctx, providerID, scope, reset)` after quota responses. Choose the scope from server-owned credential/account metadata, not an HTTP caller's scope parameter. Return `provider.RateLimitError{ResetAt: reset}` when gated so the shared job scheduler handles the delay. Distinct providers remain isolated even if their scope strings are identical.

Tests cover concurrent max-reset updates through real Redis, independent instances, provider/credential isolation, expiry, malformed stored timestamps, local fallback after Redis failure, cancellation, memory bounds, token rotation and suppressed upstream requests. These gates coordinate known limits; they do not serialize requests that were already in flight when the first quota response arrived.

Legacy quota import needs no credential export or Redis-wide scan. It uses the server's existing authenticated credential binding. Ten contracts execute the TypeScript token-key function and registration scope expressions, covering ordinary credentials, anonymous requests, installations, App users and Unicode tokens. Integration tests seed those exact Redis keys and verify suppressed HTTP calls, import persistence across Go instances and renewed credentials, unchanged legacy values/expiries, max-reset handling, cancellation and expiry. Malformed, noninteger, expired and out-of-range timestamps are ignored. The bridge is one-way: new Go quota observations are not written back into TypeScript's namespace. BullMQ jobs still require a separate handoff.

### Offline BullMQ handoff

`node backend/scripts/migrate-bullmq.cjs` defaults to a dry run. Run it from a checkout with `npm ci` dependencies installed. Set `MONGODB_URI`, `MONGODB_DATABASE`, `REDIS_HOSTNAME` and `REDIS_PORT` to the same services and database used by the application. The database name is required explicitly. The command reads the application's three queue names through the installed BullMQ library and never decodes or edits private Redis job records.

1. Block new writes and take verified MongoDB/Redis/storage backups. Run `node backend/scripts/migrate-bullmq.cjs pause`. It pauses the three BullMQ queues and Go queue controls. Already running jobs are not cancelled.
2. Let active jobs finish, then stop all Node and Go producers, workers, streamers and scheduled writers. A paused queue still accepts new jobs, so pausing alone is insufficient. The tool checks for connected BullMQ workers, active Go jobs and unpaused queues; those checks cannot prove that every external producer has stopped.
3. Run `node backend/scripts/migrate-bullmq.cjs dry-run`. Review the job counts, resource-transition count and source digest. No job/resource/checkpoint documents are written by a dry run. Resolve conflicting existing Go work before applying.
4. Run `node backend/scripts/migrate-bullmq.cjs apply`. Require a successful exit and `complete: true`. If interrupted, keep both runtimes stopped and rerun the same command. A process killed outright can retain its migration lock for up to one minute. The snapshot digest must remain unchanged; investigate a changed snapshot instead of deleting the checkpoints.
5. Start Go with its queues still paused, inspect the imported queue and resource states, and run the staging smoke checks. Resume Go queues through the admin controls once those checks pass. Keep the Node queues paused. Retain their records and backups until the cutover is accepted.

Each source job gets its own stable Go ID and import checkpoint, including duplicate jobs for one repository. Waiting order, priorities, future availability, attempt counts, fixed/exponential backoff and configured retry limits are retained. Failed history is imported as failed; its public error is sanitized to `job_failed`, and raw payload fields, exception text and stack traces are not copied. Missing repositories produce failed jobs rather than recreated resources. Live preparation jobs transition eligible resources to `preparing`; live removal requests transition them to `removing`. Removal wins when both actions are pending. Terminal resources are not revived by preparation jobs. Resource changes use revision guards. The ordinary Go enqueue path recognizes imported live jobs and does not add duplicate maintenance work.

`gojobimports` records the frozen source digest and each resource/job checkpoint. A retry after an interrupted write completes the checkpoint without resetting an existing Go job. Completed checkpoints also prevent jobs deleted later by an administrator from being recreated. An atomic Redis lease prevents simultaneous import commands. Source queue jobs are never removed or resumed by the tool. Custom backoff functions, jitter, LIFO, dependency flows and recurring schedules are rejected explicitly; the current application does not create these, and they need a separate design if introduced.

Before Go workers run, rollback can use the verified pre-cutover backup and paused source queues. After Go has processed imported work or accepted writes, resuming the retained BullMQ snapshot would replay work. Stop Go and reconcile queue/resource changes using the rollback procedure above; retaining the source snapshot does not make that later rollback automatic.

The integration suite creates real BullMQ jobs in disposable Redis, imports them into disposable MongoDB, injects interruption after resource and job writes, and then runs Go workers against a non-GitHub provider. It covers duplicates, priority order, delayed eligibility, retry success/exhaustion, completed-checkpoint replay prevention, sanitized history and unsafe preconditions. This is an automated rehearsal, not evidence of a production cutover.

Imported failed removal jobs receive an automatic recovery pass at Go worker startup, matching TypeScript's startup recovery intent. A paused startup pass remains pending until maintenance observes that the queue has resumed. It leaves active jobs and unrelated failed jobs alone and records `migration.removalRecovered` so periodic maintenance cannot repeatedly reset an exhausted imported job. A later process startup can retry it again, as TypeScript does. Normal cleanup maintenance still handles resources already in `removing`.

Both automatic and admin-requested retries recheck the resource immediately before cleanup. An imported removal can recover an `error` resource only when its anonymization date is absent or no newer than the source job, or when its current owner is still banned. Already removed resources are not revived. Without a current owner ban, restored ready resources and newer preparation errors are left alone. MongoDB date comparisons retain TypeScript's treatment of null/string values. Revision checks also protect owner transfers, provider-binding replacement and anonymization-date changes during the claim. Tests cover single, bulk and automatic retries, pause/resume behavior, stale requests and a real failed BullMQ removal imported and completed by a Go worker.

Repository removal and expiry snapshot exact storage object names and MongoDB row IDs, then verify the resource revision before deleting. Duplicate workers cannot recursively delete a newer generation published after restoration. Deletions are retryable and batched in groups of 1,000 for S3 and MongoDB; filesystem deletion never descends into a captured path that has become a directory. The snapshot uses the existing 100,000-object storage-list bound and a 1,000,000-row bound per collection. Exceeding either bound leaves the resource pending cleanup and reports an error rather than deleting a partial snapshot. Empty filesystem directories can remain. This relies on Go's immutable content generation paths and read-only archive originals; Node workers and external storage writers must remain stopped after cutover. A regression test pauses a worker logically after snapshot capture, completes removal and restoration through another worker, and verifies that repeated stale cleanup preserves the new content and rows.

Go runs independent worker pools matching TypeScript: 3 download workers, 5 removal/expiry workers and 5 cache workers per process. Each pool observes only its own pause key and claims only its queue's actions. Downloads cannot occupy cleanup slots. Pausing leaves in-flight work running and prevents subsequent claims once workers observe the pause; resuming wakes idle workers within the one-second polling interval. `RunJobs` returns after cancellation has stopped all its worker loops. The TypeScript worker-capacity contract and an integration test with blocked non-GitHub downloads and blocked S3 deletions verify all three capacities, pause isolation, resumption and shutdown. Cache reset snapshots exact file names before changing its cache revision, so delayed deletion cannot erase newly fetched content under that revision. Its snapshot uses the storage listing limit of 100,000 objects; larger caches require cleanup before retry. The S3 integration test publishes a file under the new revision while deletion is blocked, then verifies that it survives.

The Go executable handles SIGINT and SIGTERM by cancelling queue work and stopping new HTTP connections, then allowing up to 30 seconds for in-flight HTTP requests and worker loops to finish. It closes the anonymization cache, storage and database only after both have stopped. A bind failure starts no workers and exits with status 1. An unexpected HTTP server stop also cancels workers and drains requests. If the grace period expires, it closes HTTP connections and exits with status 1 without closing shared dependencies underneath unfinished work. The Compose service allows 45 seconds before a forced container stop, leaving time for metric flushing and database disconnect after a successful drain. The first lookup of a masked/custom path can still pay the index-build cost; directory/index-page rendering retains the full listing fallback.

### ZIP memory

MongoDB connections default to Snappy wire compression. The driver's zstd encoder pool can retain hundreds of MiB of windows on machines with many CPUs, including during per-entry ZIP authorization queries. An explicit `compressors` option in the MongoDB URI overrides the default. ZIP payloads still use Deflate.

ZIP downloads read projected file metadata in batches of 128, with no file-count truncation. They reuse one Deflate writer and one 32 KiB copy buffer. File bodies and transformed results remain disk-backed; the ZIP central directory and duplicate-name set still grow with the number of entries. Each entry retains content authorization and revision checks. Cursor errors and cancellation abort the response rather than finalizing an incomplete archive.

### Streaming upstream archives into ZIP downloads

GitHub ZIP downloads now use one commit-pinned [tarball request](https://docs.github.com/en/rest/repos/contents#download-a-repository-archive-tar), consumed incrementally. `provider.Archives` is an optional capability; other providers and uploaded archives retain the existing per-file path. The GitHub adapter permits HTTPS redirects only to GitHub API/codeload hosts and strips the API credential on the codeload redirect. Its body deadline is 30 minutes, including client backpressure.

Three stages download and verify an entry, transform it, and compress its output into the client ZIP. Two unbuffered handoffs bound the pipeline to one downloading input, one transforming entry and one output being sent. Slow clients stop further preparation. The existing eight-transfer admission limit and worker memory limits still apply. Source entries use a reused 32 KiB copy buffer and temporary disk files, never a whole-repository spool. Regex transformation still requires an individual complete text file; it does not run on arbitrary byte chunks. ZIP central-directory and duplicate-path metadata grow with the entry count.

Git blob hashes are verified before transformation. Symlinks become regular files containing their Git blob target text; links are never followed. LFS pointers, export-subst differences and export-ignore omissions use the normal provider file path to preserve output. Missing metadata from truncated trees is resolved against the same commit. Output authorization and repository revisions are checked after preparation and before every entry is released. Cancellation, corrupt gzip/truncated input, invalid paths and duplicate anonymized names abort the response and clean up both stages; a corrupt stream is never finalized as a valid ZIP.

The integration test deliberately pauses the upstream before the second file and requires the first ZIP payload to reach the client before releasing it. It also checks cancellation, temporary-file cleanup, corrupted input, repository revocation, archive export exceptions, and zero blob requests for an ordinary streamed archive. This path requests an upstream archive on each download; the earlier local ZIP memory benchmark does not measure GitHub network latency.

ZIP requests have a 30-minute overall deadline. Other API requests retain their two-minute deadline. ZIP socket writes renew a one-minute write deadline on every write/flush, so an active slow transfer can outlive the HTTP server's ordinary two-minute write timeout while a stalled socket still expires. Tests cover an expired server write deadline between ZIP entries and a client that stops reading entirely. Stream failures now log a fixed stage and reason with the request ID, distinguishing client cancellation, request expiry, I/O timeouts and preparation failures without exposing source paths, URLs or credentials.

Anonymization workers now release execution slots and memory reservations as soon as the child has exited and its output is on disk, including cache hits. Output file handles remain valid until the caller's cleanup. A slow reader therefore cannot hold the only worker slot and cause another transform to hit the 30-second admission timeout. Request transfer limits and the ZIP pipeline's unbuffered handoffs still bound outstanding output files. The worker test keeps multiple cold/cached outputs open with one configured worker and verifies that both execution and memory admission are available before cleanup.

Authenticated browser sessions persist for 30 days and renew on activity at most once per day, giving a 29–30 day idle lifetime. Redis expiry and the Secure/HttpOnly/SameSite=Lax cookie are renewed together. Existing valid session cookies upgrade on their next authenticated request. Renewal uses compare-and-set so it cannot resurrect a logged-out session or overwrite concurrent session changes. Account status is still checked on every request. Anonymous OAuth sessions remain browser-session cookies with a 24-hour Redis lifetime; OAuth state still expires after ten minutes. Preserve the session secret and Redis volume across deployments.
